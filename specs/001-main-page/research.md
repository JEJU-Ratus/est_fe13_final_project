# 조사 결과: 메인 페이지

## 결정 1: 페이지 상태 관리 범위

**결정**: 입력, checkbox, 모달, 요청 중 상태가 필요하므로 `src/app/page.js`를 Client
Component로 구성한다.

**근거**: 현재 페이지는 자리표시자 수준이고, 페이지 전체가 하나의 상호작용 흐름을 구성한다.
추가 하위 폴더나 명세에 없는 추상화 없이 가장 단순하게 구현할 수 있다.

**검토한 대안**: Server Component 페이지와 별도 Client Component 추가. 현재 범위에서는 파일과
추상화만 늘어나므로 선택하지 않았다.

## 결정 2: 인증·요약 생성 연결 경계

**결정**: 페이지는 `authenticated` 여부를 입력으로 받고, 유효한 생성 요청을 보내며,
성공·실패 결과를 처리해야 한다는 논리 계약만 확정한다. Supabase 클라이언트, API 경로,
Server Action 여부는 정하지 않는다.

**근거**: `AGENTS.md`는 구체적인 명세 없이 Supabase 인증·데이터베이스·서버 통신 구조를
임의로 구현하지 못하게 한다.

**검토한 대안**: 클라이언트에서 Supabase 직접 호출, Route Handler, Server Action. 모두 세부 통신
구조를 임의로 결정하므로 보류했다.

## 결정 3: 입력 검증

**결정**: 주제는 앞뒤 공백을 제거한 후 1~200자를 허용한다. 비밀번호 사용 시 숫자
4자리만 허용한다. 비밀번호 사용을 해제하면 현재 값이 남아 있어도 요청에 포함하지
않는다.

**근거**: `FR-003`, `FR-005`, `FR-006`에서 검증 규칙과 전송 조건을 확정했다.

**검토한 대안**: 추가 공통 검증 라이브러리. 하나의 간단한 폼에 불필요하고 승인되지 않아
사용하지 않는다.

## 결정 4: 공통 UI와 페이지 전용 UI 경계

**결정**: Header, Banner, `SuggestLoginModal`, `PreparingModal`, `QuickLinkCard`는 공통 명세와
구현이 있을 때 재사용한다. 생성 입력, 로딩 모달, 오류 모달은 일단 페이지 전용 요소로
유지한다.

**근거**: `AGENTS.md`가 정의한 공통 컴포넌트 목록을 존중하면서 명세에 없는 공통화를
피한다. 현재 `src/components`에는 재사용할 파일이 없다.

**검토한 대안**: 모든 메인 UI를 즉시 공통 컴포넌트로 생성. 다른 페이지의 요구사항과 영향
범위가 확인되지 않아 선택하지 않았다.

## 결정 5: 검증 전략

**결정**: 현재 제공된 ESLint와 Next.js build를 정적 관문으로 사용하고, 사용자 스토리는
지정된 수동 시나리오로 검증한다.

**근거**: 프로젝트에 테스트 러너가 없고, 사용자가 추가 패키지나 테스트 도입을 요청하지
않았다.

**검토한 대안**: 새 단위·E2E 테스트 도구 도입. 현재 승인 범위와 헌법에 맞지 않아
보류했다.

## 보류된 외부 결정

- Header 상세 및 사이드바 여부: 참조된 `header.md`가 없으므로 공통 UI 명세에서 확정한다.
- 인증 상태 제공 방식: 인증 명세에서 확정한다.
- 요약 생성 통신 방식과 실패 메시지 문구: 서버 계약에서 확정한다.
- 배너 URL과 자산 배치 경로: 배포 전 콘텐츠·자산 명세에서 확정한다.
- 성공 기준 `SC-001`, `SC-002`, `SC-006`의 사용자 시간·비율 측정: 별도 사용성 조사가 있을
  때만 수행하며, 현재 기능 인수에서는 정성적 참고로만 사용한다.
