# 빠른 시작 및 검증 안내: 학습노트 전체 목록

## 목적

두 전체 목록 경로가 같은 화면 계약을 지키면서 범위별 데이터만 다르게 조회하는지 확인한다. 데이터 필드와 상태 전이는 [데이터 모델](./data-model.md), 조회·오류·라우트 동작은 [인터페이스 계약](./contracts/all-notes-contract.md)을 따른다.

## 사전 조건

- 프로젝트 의존성이 설치되어 있다.
- 기존 Supabase 환경을 사용하는 경우 `.env.local`에 팀이 제공한 URL과 Publishable Key가 설정되어 있다. Secret Key와 `service_role` Key는 사용하지 않는다.
- 기존 `002-summary-detail` 데이터 조회 계약 또는 개발용 mock 어댑터가 연결되어 있다.
- 검증 데이터에 다음 항목이 준비되어 있다.
  - 현재 사용자 본인의 학습노트 25개 이상
  - 공개 요약본 1개에 연결된 학습노트 25개 이상
  - 잠긴 요약본 1개와 비밀번호 인증 전·후 세션 상태
  - 같은 `createdAt`을 공유하지만 서로 다른 `noteId`를 가진 항목
  - 항목이 0개인 목록 범위
  - 존재하지 않는 `summaryId`
  - 이미지와 목적지 URL이 모두 있는 배너, 각각 하나씩 누락된 배너 데이터

검증용 데이터는 승인된 기존 서비스나 테스트 어댑터로 준비하며, 이 기능의 quickstart를 위해 마이그레이션·seed 파일을 추가하지 않는다.

## 실행

```bash
npm install
npm run dev
```

### UI-first mock 실행 순서

T001–T025의 UI MVP는 Supabase·DB·실제 비밀번호 서비스에 연결하지 않고
`src/mocks/all-notes.js`의 `loadMockStudyNotePage`와 접근 상태 mock을 사용한다.
따라서 UI 검증은 다음 순서로 진행한다.

1. 개발 서버를 실행하고 아래 mock 식별자로 공개·잠금·빈·오류·없는 요약본을 각각 연다.
2. 첫 응답의 총 개수와 12개 행을 확인한 뒤, 목록 끝까지 이동해 cursor 단위 추가 조회와 중복 제거를 확인한다.
3. 잠금 요약본에서는 목록이 노출되지 않은 상태에서 비밀번호 모달을 확인하고, 4자 미만 입력은 실패·4자 이상 입력은 성공으로 확인한다.
4. UI-first mock은 비밀번호 원문이나 고정 비밀번호를 저장하지 않으며, 인증 성공 여부는 실행 중 메모리에서만 유지한다. 실제 세션 인증 연결은 T026 이후 범위다.

| 검증 목적 | mock 식별자 또는 경로 | 예상 데이터·상태 |
|---|---|---|
| 공개 요약본 | `/summary/summary-001/notes` | 60개 이상, 비로그인 목록 허용 |
| 잠금 요약본 | `/summary/summary-002/notes` | 31개, `passwordRequired` → `authorized` |
| 빈 목록 | `/summary/summary-empty/notes` | 0개, `EmptyState`만 표시 |
| 일반 오류 | `/summary/summary-error/notes` | `CommonModal` 500 오류 |
| 없는 요약본 | `/summary/summary-not-found/notes` | `CommonModal` 404 후 `/` 이동 |

`MOCK_BANNERS`에는 유효한 내부·외부 목적지, 목적지 누락, 이미지 누락 변형이 있으며,
같은 작성 시각을 가진 항목과 12개 단위 페이지도 함께 준비되어 있다. `/mypage/summaries`는
현재 담당자 구현 범위로 제외되어 이 브랜치에서는 페이지 파일을 유지·수정하지 않는다. 아래
요약본 경로 검증을 먼저 진행하고, 마이페이지 담당자가 경로를 다시 연결한 뒤 시나리오 1·5·7을
추가로 실행한다.

브라우저에서 다음 경로를 직접 연다.

```text
/summary/{공개-summaryId}/notes
/summary/{잠긴-summaryId}/notes
/summary/{존재하지 않는-summaryId}/notes
```

## 시나리오 1: 내 학습노트 목록

1. 로그인한 상태로 `/mypage/summaries`를 연다.
2. 상단에 `총 {count}개의 학습노트`가 표시되는지 확인한다.
3. 첫 화면에 최신 작성일 순으로 최대 12개가 표시되는지 확인한다.
4. 각 행에 퀴즈 상태 이미지, 작성자 닉네임, 주제, `YYYY.MM.DD` 작성일이 표시되는지 확인한다.
5. 행을 선택해 해당 `summaryId`와 `noteId`의 `/summary/{summaryId}/notes/{noteId}`로 이동하는지 확인한다.

**예상 결과**: 퍼센트 값이나 별도 CTA 없이 목록과 상세 이동이 정확히 표시된다.

## 시나리오 2: 12개 단위 추가 조회와 중복 방지

1. 25개 이상의 항목이 있는 목록에서 첫 12개가 표시될 때까지 기다린다.
2. 목록 끝으로 스크롤해 다음 묶음을 요청한다.
3. 같은 위치에서 빠르게 여러 번 스크롤하거나 sentinel이 계속 보이는 상태를 만든다.
4. 두 번째 묶음이 한 번만 요청되고 첫 묶음과 중복되지 않는지 확인한다.
5. 마지막 묶음이 1개이거나 12개 미만일 때 추가 감시가 종료되는지 확인한다.
6. 같은 작성 시각의 항목이 누락되지 않고 `noteId` 보조 정렬 순서를 유지하는지 확인한다.

**예상 결과**: 화면에는 중복 행이 없고, 더 가져올 데이터가 없으면 추가 요청이 발생하지 않는다.

## 시나리오 3: 공개 요약본 목록

1. 로그아웃 또는 비로그인 상태로 `/summary/{공개-summaryId}/notes`를 연다.
2. 로그인 요구 모달 없이 전체 개수, 행 목록 또는 빈 상태가 표시되는지 확인한다.
3. 행 선택 시 상위 `summaryId`가 동일한 상세 경로로 이동하는지 확인한다.

**예상 결과**: 공개 요약본의 목록은 로그인 여부와 무관하게 조회된다.

## 시나리오 4: 잠긴 요약본의 세션 인증

1. 비밀번호 인증이 없는 브라우저 세션에서 `/summary/{잠긴-summaryId}/notes`를 연다.
2. 목록이 노출되지 않고 `NotePwModal`이 표시되는지 확인한다.
3. 잘못된 비밀번호를 제출해 인라인 오류와 재입력 상태를 확인한다.
4. 올바른 비밀번호를 제출하고 목록이 표시되는지 확인한다.
5. 같은 브라우저 세션에서 페이지를 다시 열어 재인증 없이 목록이 표시되는지 확인한다.
6. 다른 브라우저 세션에서 같은 경로를 열어 다시 인증이 필요한지 확인한다.

**예상 결과**: 인증 전 보호된 항목 노출은 0건이며, 세션 인증 결과는 기존 잠금 서비스의 정책을 따른다.

## 시나리오 5: 비로그인 내 목록 접근

1. 로그아웃 상태로 `/mypage/summaries`를 연다.
2. 목록 내용이 모달 뒤에 노출되지 않는지 확인한다.
3. 모달을 즉시 닫거나 그대로 둔 뒤 접근 시점부터 3초가 지나도록 기다린다.

**예상 결과**: 접근 제한 모달이 표시되고 `/login`으로 이동한다.

## 시나리오 6: 빈 목록

1. 항목이 0개인 내 목록 또는 요약본 목록을 연다.
2. `학습 노트 리스트가 아직 생성되지 않았습니다.`가 한 번 표시되는지 확인한다.
3. 목록 행, 추가 로딩 sentinel, 생성·작성 CTA가 함께 표시되지 않는지 확인한다.

**예상 결과**: 정상 빈 결과에서만 기존 `EmptyState`가 표시되고 오류·로딩 상태와 섞이지 않는다.

## 시나리오 7: 오류와 없는 요약본

1. 일반 목록 조회가 실패하도록 기존 개발 어댑터 또는 테스트 환경을 설정한다.
2. `/mypage/summaries`와 `/summary/{summaryId}/notes`에서 각각 오류 모달을 확인한다.
3. 모달을 닫은 뒤 각각 `/mypage`, `/summary/{summaryId}`로 이동하는지 확인한다.
4. 존재하지 않는 식별자의 `/summary/{없는-summaryId}/notes`를 연다.

**예상 결과**: 없는 요약본은 공통 오류 모달을 표시하고 3초 뒤 `/`로 이동한다. 추가 로딩 실패 시 이미 표시한 행은 사라지지 않는다.

## 시나리오 8: 배너와 데스크톱 레이아웃

1. 이미지와 목적지 URL이 모두 유효한 배너를 선택해 지정된 내부 또는 외부 목적지로 이동하는지 확인한다.
2. 이미지 또는 목적지 URL이 없는 배너가 이동 가능한 링크가 아닌지 확인한다.
3. 1440px 데스크톱 프레임에서 Header가 펼친 상태로 시작하는지 확인한다.
4. 긴 닉네임과 주제를 넣어도 행 열 경계와 전체 레이아웃이 깨지지 않는지 확인한다.
5. 모바일·태블릿 전용 동작이나 별도 레이아웃이 추가되지 않았는지 확인한다.

## 정적 검증

```bash
npm run lint
npm run build
git diff --check
```

**통과 기준**:

- lint와 production build가 성공한다.
- 두 경로에서 총 개수, 최신순, 12개 단위 추가, 중복 0건이 확인된다.
- 인증 전 잠긴 목록과 비로그인 내 목록의 보호 콘텐츠 노출이 0건이다.
- 빈 목록·일반 오류·없는 `summaryId`의 문구와 후속 이동이 계약과 일치한다.
- 기존 `NoteItem`, `Banner`, `EmptyState`, `CommonModal`, `NotePwModal`, Supabase 공통 클라이언트의 범위를 벗어난 변경이 없다.
