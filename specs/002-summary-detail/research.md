# 조사 결과: 요약 및 학습노트 상세

## 결정 1: 동적 경로와 공통 레이아웃

**결정**: 실제 저장소 경로인 `src/app/(site)/Summary/[summaryId]/layout.js`에서 생성 주제와 AI 요약을 공통으로 구성하고, 요약 상세·작성·학습노트 상세·수정 페이지는 명세에 정의된 하위 `page.js`에 둔다. Next.js 16의 동적 `params`는 비동기 값으로 해석한다.

**근거**: 기능 명세와 `AGENTS.md`가 네 경로와 공통 레이아웃 위치를 직접 지정한다. 최신 App Router 문서의 동적 페이지 예시는 `params`를 Promise로 받고 `await`한 뒤 식별자를 사용한다.

**검토한 대안**: 각 페이지가 요약 정보를 중복 조회·렌더링하면 공통 영역과 잠금 판정이 분산된다. 별도 하위 컴포넌트 폴더는 프로젝트 구조 규칙에 어긋나 제외한다.

## 결정 2: Server/Client Component 경계

**결정**: 페이지와 레이아웃은 기본 Server Component를 유지하고, 입력 상태·이벤트·모달·북마크·퀴즈처럼 브라우저 상호작용이 필요한 최소 경계만 Client Component로 둔다.

**근거**: Next.js는 레이아웃과 페이지를 기본 Server Component로 처리하며 상태, 이벤트, Effect, 브라우저 API가 필요한 경우에만 Client Component를 권장한다. 이는 불필요한 클라이언트 번들을 줄이고 프로젝트 규칙의 제한적 `"use client"` 사용과 일치한다.

**검토한 대안**: 요약 레이아웃 전체를 Client Component로 만들면 공통 정적 콘텐츠까지 클라이언트 경계에 포함되고 직렬화 가능한 props 제약이 넓어진다.

## 결정 3: 존재하지 않는 식별자 처리

**결정**: 요약본 또는 학습노트를 찾을 수 없으면 해당 Server Component 경계에서 `notFound()`를 호출하고 프로젝트의 기본 404 UI를 사용한다.

**근거**: 명세는 찾을 수 없음 페이지를 요구한다. Next.js의 `notFound()`는 현재 라우트 세그먼트 렌더링을 종료하고 404 처리를 제공하므로 새 오류 상태나 조건부 클라이언트 이동이 필요 없다.

**검토한 대안**: `useRouter`로 메인 화면에 보내면 404 요구를 충족하지 않고 잘못된 식별자를 숨긴다. 별도 `not-found.js` 추가는 전용 디자인 명세가 없어 제외한다.

## 결정 4: 정적 링크와 결과 기반 이동

**결정**: 학습노트 항목, `더보기`, 작성·수정 버튼처럼 목적지가 이미 정해진 이동은 `Link`를 사용한다. 생성·수정·삭제 응답, 접근 권한과 모달 취소 결과에 따른 이동만 `useRouter`를 사용한다.

**근거**: Next.js는 `Link`를 기본 탐색 수단으로 권장하고 사전 로드와 클라이언트 전환을 제공한다. 프로젝트 규칙도 정적 목적지는 `Link`, 조건부 목적지는 `useRouter`로 구분한다.

**검토한 대안**: 모든 이동을 클릭 이벤트와 `router.push`로 통일하면 정적 링크의 의미와 사전 로드를 잃는다.

## 결정 5: 인증·데이터 서비스 경계

**결정**: 이번 계획은 화면이 필요로 하는 연산과 데이터 모양을 계약으로 정의하되 Supabase 클라이언트, 테이블, Route Handler, Server Action 또는 별도 데이터 모듈을 선택하지 않는다. 구현 전 기존 서비스가 계약을 제공해야 한다.

**근거**: 헌법과 `AGENTS.md`는 구체적인 Supabase 인증·데이터베이스·통신 명세가 없을 때 구조를 임의로 구현하지 못하게 한다. 현재 코드에는 요약 상세 데이터 계층이 없다.

**검토한 대안**: 임시 Supabase 스키마나 `fetch` URL을 정하면 승인되지 않은 통신 구조가 된다. 제품 경로에 하드코딩한 데모 데이터는 실제 권한·삭제·잠금 검증을 왜곡한다.

## 결정 6: 잠금 인증 상태 소유권

**결정**: 동일 브라우저 세션의 요약본 인증 완료 상태는 외부 인증 서비스가 소유하고, UI는 `isSummaryVerified` 결과만 받는다. 원문 비밀번호는 검증 요청 외에 저장하지 않는다.

**근거**: 명세는 동일 브라우저 세션과 하위 경로에서 인증을 공유하도록 요구하지만 세션 저장 방식은 정의하지 않는다. 기존 `NotePwModal` 계약도 세션 소유권을 호출 측 또는 별도 인증 계층에 둔다.

**검토한 대안**: `localStorage`나 전역 React 상태에 비밀번호 또는 인증 플래그를 직접 저장하면 보안·만료·새 탭 동작을 임의 결정하게 된다.

## 결정 7: 기존 공통 컴포넌트 재사용

**결정**: 삭제 확인·로그인 제안·시스템 오류는 `CommonModal`, 잠금 입력은 `NotePwModal`, 이벤트 요청은 `Loading`, 공통 탐색은 `Header`의 현재 공개 계약을 재사용한다.

**근거**: 각 컴포넌트와 UI 계약이 저장소에 존재하고 요약 상세 명세의 요구를 이미 포함한다. 중복 컴포넌트 생성과 공개 props 변경 없이 호출부 상태만 소유할 수 있다.

**검토한 대안**: 페이지별 모달과 로딩을 새로 만들면 같은 역할을 중복하고 공통 컴포넌트 우선 규칙을 위반한다.

## 결정 8: 이벤트 요청과 오류 보존

**결정**: 생성·수정·삭제·북마크 요청은 호출 측 Boolean 요청 상태로 중복 실행을 막고 `Loading`을 한 번만 표시한다. 실패 시 요청 상태를 종료하고 입력 또는 현재 페이지 상태를 유지한 채 정규화된 상태로 `CommonModal error`를 표시한다.

**근거**: 기능 명세와 기존 Loading·CommonModal 계약이 이 소유권을 직접 요구한다. 요청 상태를 호출부가 관리하면 성공·실패 모두에서 명확히 해제할 수 있다.

**검토한 대안**: 전역 로딩 Provider나 데이터 요청 라이브러리는 승인되지 않은 구조·패키지를 추가한다. 실패 후 페이지를 무조건 새로고침하면 입력 보존 요구를 위반한다.

## 결정 9: 양식 검증

**결정**: 제목과 세 본문 값을 blur 및 제출 전에 정규화한다. 제목은 공백 제거 후 필수·최대 50자, 세 본문은 선택·각 최대 1,000자를 검증하고 오류가 있으면 요청하지 않는다.

**근거**: 명세가 검증 시점, 공백 처리, 필수 여부와 길이를 모두 확정한다. 브라우저 기본 검증 문구 대신 명세 문구와 SCSS 상태를 제어해야 테스트가 일관된다.

**검토한 대안**: 제출 시에만 검증하면 blur 오류 요구를 충족하지 않는다. 서버 검증만 의존하면 불필요한 잘못된 요청이 발생한다.

## 결정 10: 퀴즈 모달 책임

**결정**: `QuizModal`은 저장된 퀴즈를 받아 답안 선택·단일 제출·채점 결과·닫기만 관리한다. 퀴즈 생성과 영속 저장은 포함하지 않는다.

**근거**: 명세는 미리 저장된 퀴즈 사용을 요구하고 프로젝트 구조는 `QuizModal.jsx`를 공통 컴포넌트로 지정한다. UI 책임을 제한하면 서비스 계약과 표시 계약이 분리된다.

**검토한 대안**: 모달에서 퀴즈 생성이나 원격 저장까지 수행하면 명세 범위와 UI 컴포넌트 책임을 넘어간다.

## 결정 11: 검증 도구

**결정**: 기존 `npm run lint`, `npm run build`와 수동 경로 시나리오를 사용하고 새 테스트 패키지를 설치하지 않는다.

**근거**: 현재 `package.json`에는 ESLint와 Next.js 빌드만 있으며 테스트 프레임워크가 없다. 계획 단계에서 새 라이브러리를 선택할 권한이 없다.

**검토한 대안**: Jest, Vitest 또는 브라우저 자동화 패키지 추가는 요청되지 않은 의존성 도입이다.
